# E-4 장기 로드맵 — bb 교훈의 본격 이식

**작성일:** 2026-08-19
**상태:** 분리 완료 (갭 E 본선 4.1절 6번 "별도 계획 분리" 충족). 본 문서의 항목들은
[SELF_EVOLUTION_PLAN.md](SELF_EVOLUTION_PLAN.md) 3.4절에서 분리된 장기 항목이며,
**고정 일정이 아닌 조건 기반 시공** 대상이다.

---

## 0. 분리 배경

갭 E 본선(E-0a → E-3)이 완료되면서 자기 적용의 최소 안전 루프
(제작 → 격리 → 검증 → 승인 → 편입 → 재시작 반영)는 닫혔다.
3.4절의 E-4 항목들은 이 루프를 **강화·확장**하는 장기 투자로,
본선에 남겨두면 시공 순서가 왜곡되므로 별도 문서로 분리한다.

각 항목은 독립 갭으로 취급한다. 시공 시에는 본선과 동일한 규율을 따른다:
프로브 작성 → 통과 → git commit+push → 이 문서와 본 문서 상태 갱신.

## 2. 항목별 시공 초안

### E-4a — worktree 격리 (E-L3의 기반)

**현 상태:** 자기 수정은 [`SelfModifyPipeline`](../api/api/dynamic/self_modify.py)의
체크포인트+롤백(`git reset --hard` + `clean -fd`)으로 보호된다.
그러나 수정이 **현재 워크트리 위에서** 일어나므로, 롤백이 실패하거나
사용자 미커밋 작업과 섞이면 오염 범위가 워크트리 전체다.

**목표:** 자기 수정 실험을 전용 브랜치+worktree에서 수행하고,
검증 통과 시에만 주 워크트리로 병합. bb의 "스레드마다 새 브랜치+복사본,
아카이브 시 자동 정리" 패턴을 DAON의 자기 수정 파이프라인에 맞게 축소 이식.

**시공 초안:**
1. `git worktree add`로 격리 워크트리 생성 (브랜치: `self-modify/<run_id>`)
2. `SelfModifyPipeline`의 apply/probe 단계를 격리 워크트리에서 실행
   (기존 `git_runner`/`probe_runner` 주입점에 cwd만 교체 — 인터페이스 변경 없음)
3. 검증 통과 → 주 워크트리 병합(또는 체리픽) + worktree 제거
4. 실패/거부 → worktree 강제 제거(`git worktree remove --force`)로 완전 격리 폐기
5. Windows 경로 주의: worktree 경로는 레포 루트 밖이되 `%TEMP%`가 아닌
   관리 디렉터리(예: `STATE_DIR/worktrees`)에 두고, 아카이브 시 자동 정리

**검증 방법:** 프로브 — 격리 생성/병합/폐기 전 구간을 페이크 git 러너로 모의 +
실제 임시 레포에서 `git worktree` 통합 확인.

**시공 트리거:** E-L3(격리 갭) 시공 시 함께 수행. E-L3의 "워크스페이스 안전 불변식"
검증이 worktree 없이는 불완전하므로, E-L3 착수 = E-4a 착수.

### E-4b — 에이전트용 CLI 표면 (`daon` CLI)

**현 상태:** 하네스 잡 시작은 웹 UI(POST `/api/dynamic/run`)로만 가능.
에이전트가 스크립트/서브프로세스에서 잡을 띄우는 1급 통로가 없다.

**목표:** bb의 "CLI를 에이전트용 1급 표면으로 노출" 철학을 이식 —
`daon run <task>` / `daon status <run_id>` / `daon approve <run_id>` 같은
최소 CLI로 기존 HTTP API를 재호출. 새 런타임이 아니라 기존 서버 API의 얇은 래퍼.

**시공 초안:**
1. `hermes-agent/daon_cli.py` (또는 동등 진입점) — argparse 서브커맨드
2. `run`: POST /api/dynamic/run 호출 후 run_id 출력 (JSON 모드 지원)
3. `status`: GET /api/dynamic/status/{run_id} 폴링
4. `approve`/`answer`/`cancel`: 기존 동적 라우트 재호출
5. 서버 주소/포트는 기존 config와 동일 해석(dev/포터블), 인증은 로컬 전용

**검증 방법:** 프로브 — HTTP 계층을 페이크로 모의한 커맨드 파싱/출력 계약 검증 +
실서버 통합은 실기기 검증 단계에서 수행.

**시공 트리거:** E-L2(Builder Agent 역할화) 이후. Builder 서브팀이 제작 산출물을
검증 루프에 올리려면 스크립트 가능한 진입점이 필요해지는 시점이 자연스러운 착수점.

### E-4c — SQLite 영속 상태

**현 상태:** 잡 레지스트리(`api/api/dynamic_jobs.py`의 `_DYNAMIC_JOBS`)는 인메모리.
서버 재시작(E-3로 자동화됨) 시 진행 중 잡의 메타데이터는 사라진다.
(스레드 자체는 복원 불가 — 재시작 후 "잡이 있었음"을 복원하는 것이 목표.)

**목표:** 잡/라인지/승인 이력의 최소 스키마를 SQLite에 기록해,
재시작 후 상태 조회·표시가 가능하게 함. bb의 영속 상태 교훈을
DAON의 파일 기반 STATE_DIR 체계 위에 얹음.

**시공 초안:**
1. DB 위치: `STATE_DIR/daon_state.db` (dev/포터블 경로 해석 자동 상속)
2. 최소 스키마: `jobs(run_id, status, task, created_at, updated_at)`,
   `lineage(run_id, parent_run_id, root_run_id)`, 기존 파일 기반 상태와
   **이중 기록하되 읽기는 기존 우선**(마이그레이션 위험 최소화)
3. 재시작 시 `running` 상태로 남은 잡은 `error(interrupted by restart)`로 정리
4. E-3 오케스트레이터 사이클 결과도 선택 기록(감사 추적)

**검증 방법:** 프로브 — 임시 DB로 기록/조회/재시작 정리 시나리오 검증.
실서버 통합은 실기기 검증 단계에서 수행.

**시공 트리거:** E-3가 실기기 검증으로 안정 확인된 후. 재시작이 일상화가 되어야
영속 상태의 가치가 실현되므로, E-3 실기기 검증 완료가 선행 조건.

## 3. 공통 규율

- 각 항목 시공 시: 프로브 먼저(또는 동시) → py_compile/프로브 통과 →
  git commit+push → 본 문서 상태 갱신 → SELF_EVOLUTION_PLAN.md 교차 기록
- `_tmp_*` 파일은 미추적 유지, 빌드 전 push, 서버 무단 재시작 금지 등
  기존 운영 정책 전부 적용
- 세 항목 간 강제 순서는 없으나, 의존 관계상 **E-4a(=E-L3 동반) → E-4b → E-4c**
  순서가 자연스럽다
