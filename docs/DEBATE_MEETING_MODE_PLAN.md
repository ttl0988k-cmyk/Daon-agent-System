## 1. 배경

대표님 요청: "토론챗을 지금처럼 유지해야 하는지, 아니면 회의 방식으로 서로 다른
에이전트끼리 대화가 가능하게 해야 하는지"

과거 이슈: 토론 진행 중 서버 사망 (한 모델이 글을 쓰고 다음 모델이 답해야 하는
순차 구조에서 멈춤 → 서버 전체 불안정 시절과 겹침)

## 2. 현황 분석 — [`debate_routes.py`](../api/api/routes/debate_routes.py)

### 현재 구조
- 3라운드 상태 머신: ①각 모델 주장(순차) → ②상호 반박(순차) → ③판사 판결
- SSE 스트림(STREAMS 큐) + 프런트엔드 `debate_token` 리스너 ([`chat.js`](../static/modules/chat.js))
- 라운드 사이 사용자가 "다음 라운드" 버튼을 눌러야 진행

### 발견된 취약점 4가지 (서버 사망 원인으로 추정)

| # | 취약점 | 위치 | 위험 |
|---|--------|------|------|
| V1 | LLM 호출 타임아웃 없음 — `_execute_debate_llm`이 무한 블로킹 | debate_routes.py:43 | 한 모델이 멈추면 토론 영구 정지 |
| V2 | `get_session()`이 try 블록 밖 — 예외 시 스레드 조용히 사망 | debate_routes.py:115 | 화면 영구 대기, 에러 이벤트 미발송 |
| V3 | 세션 에이전트 락 미적용 — 일반 채팅과 동시 실행 시 메시지 손상 가능 | debate_routes.py:151/207/263 | 같은 세션 병렬 접근 시 데이터 경쟁 |
| V4 | 하트비트 미전송 — 긴 LLM 호출 중 SSE 침묵 | _run_debate_round_thread 전반 | 프런트엔드 감시 타이머 오판 여지 |

## 3. 업계 조사 결과 (2026-08-24 기준)

### Hermes Agent v0.20.5 (NousResearch, 2026-08-21 릴리스)
직접 소스 확인 완료:

**MoA (Mixture of Agents)** — `agent/moa_loop.py` (2,454줄):
- ThreadPoolExecutor로 어드바이저(참고 모델)들을 **병렬 동시 호출**
- 각 어드바이저는 도구 없이 순수 의견만 생성
- **통합자(aggregator)** 가 전체 의견을 받아 최종 답변 합성
- 개인정보 필터(이메일/전화 마스킹), 어드바이저별 독립 비용 계산, trace 파일
- 핵심 철학: *"일반 에이전트 루프가 주인이다"* — MoA는 한 턴에 끼어들어 참고 의견 수집

**Subagent 위임** — `agent/subagent_lifecycle.py`:
- 부모→자식 목표 위임 공식 계약 API
- 상태 머신(PENDING→STARTING→…), 타임아웃, 크기 제한, 보안 서명(HMAC)

### Codex 생태계
- "workflow-governor" 플러그인: 병렬 멀티 에이전트 + DAG 기반 작업 흐름 + 내구성 루프
- 자유 채팅이 아닌 **통제된 오케스트레이션**이 트렌드

### 업계 공통 결론
> **"에이전트들이 자유롭게 채팅하는 방"은 아무도 만들지 않았다.**
> 이유: 비용 폭발 + 무한 동의 루프 + 느림.
> 정석은 **오케스트레이터(사회자)가 발언권을 통제하고, 병렬 수집 후 통합**하는 구조.

## 4. 발전 계획 — 4단계

### 1단계: 안정화 (선행 필수)
| 항목 | 구현 |
|------|------|
| 타임아웃 | `_execute_debate_llm`에 120초 제한 (ThreadPoolExecutor.future.result(timeout=)) — 타임아웃 시 해당 모델 건너뛰고 `[응답 없음]` 기록 |
| 예외 처리 | `_run_debate_round_thread` 전체를 try로 감싸고 `get_session` 포함 — 어떤 예외든 `put('error', ...)` 발송 |
| 세션 락 | `_get_session_agent_lock(session_id)` 획득 후 진행 (일반 채팅과 동일 규칙) |
| 하트비트 | LLM 호출 대기 중 15초마다 `put('heartbeat', {})` |

### 2단계: 병렬화 (Hermes MoA 방식)
- 1·2라운드의 모델별 호출을 ThreadPoolExecutor(max_workers=len(models))로 병렬 fan-out
- 각 워커는 독립적으로 `debate_token`(sender 구분됨) 스트리밍 → 화면에서 동시에 여러 버블이 자라남
- 한 모델 실패/타임아웃이 나머지를 막지 않음
- 예상 효과: 4개 모델 기준 라운드당 속도 ~4배

### 3단계: 회의 모드 (신규 UI/UX)
핵심 역할 재편:
```
[사회자(Moderator)] = 통합자 겸임
  - 전체 대화 기록을 보고 다음 발언자 지목 + 집중 질문 생성
  - 최대 N턴(예: 8턴) 예산제 — 무한 루프 원천 차단
  - 종료 판단 시 판결 단계로 전환

[참여자 에이전트들]
  - 지목되면: 전체 회의록 + 사회자 질문을 받아 답변 (도구 없음)
  - 지목 안 되면: 대기 (비용 0)

[판사] = 기존 3라운드 판결 로직 재사용
```
SSE 이벤트 확장: `debate_token`, `debate_status` 유지 + `moderator_pick`
{sender, question} 신설 → 프런트엔드에 "사회자가 OOO에게 질문" 카드 표시

세션 연동: 회의는 전용 임시 컨텍스트에서 진행하고, 메시지 저장은 기존처럼
해당 세션에 append (is_debate 플래그 유지)

### 4단계: 실행 연결 (선택 확장)
- 판결의 "추천 구현 계획안"을 하네스(`/api/dynamic/run`)에 자동 위임하는 버튼
- 이미 있는 인프라라 추가 백엔드 거의 불필요

## 5. 기술 노트

- **재사용**: STREAMS/SSE 큐, 라운드 상태 머신, 판사 프롬프트, 프런트엔드
  debate_token/debate_status 리스너 전부 유지 — 파괴적 재작성 아님
- **세션 동시 작업 시너지**: 오늘 완성한 per-session 스트림 인프라(▶ 배지,
  suspend/reattach) 덕분에 회의 중 세션 이동도 안전
- **배포 주의**: 이 계획은 백엔드(.py) 수정을 포함 → **server.exe 재빌드 필요**
  (daon-server.spec이 api/api를 exe에 번들). 자가수정 파이프라인
  (rebuild → canary → swap)으로 배포. 프런트엔드(chat.js)는 직접 복사
- **동시성 상한**: 화면 HTTP/1.1 호스트당 연결 6개 제한 → 회의 참여자는
  실질 5개 이하 권장 (SSE 1개 + API 여유분)
